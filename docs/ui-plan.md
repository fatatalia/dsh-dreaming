## 一、命名：补录 → 索引

统一用 **「索引」**，"补录"这个词只用于开发时口头交流。

| 场景 | 文案 |
|---|---|
| 首次全量 | 「正在建立索引 4,231 / 14,632」 |
| 定时增量 | 「正在更新索引（+12 条）」 |
| 完成 | 「索引已是最新（14,632 条 · 14:32 同步）」 |
| 暂停 | 「索引已暂停 · 点继续」 |

**为什么是"索引"** —— 它同时覆盖全量和增量（建立 / 更新），
且本就指「为加速检索而建的辅助结构」，语义精确。

## 二、配置项与三级开关

```yaml
memorySearch:
  semantic:
    enabled: false          # ① 总开关
    autoInject: true        # ② 自动注入（enabled 打开时默认 true）
    intervalMinutes: 10
    minScore: 0.62
    # ── 高级参数（设置页折叠）──
    candidatePool: 24
    topK: 6
    vectorWeight: 0.7       # ← textWeight 恒为 1 - 此值
    maxSnippetChars: 200
```

**三档状态：**

| `enabled` | `autoInject` | 行为 |
|---|---|---|
| `false` | — | **完全关闭**。不建索引、不挂 hook、`memory_search` 走纯关键词 |
| `true` | `false` | **只索引不注入**。索引照常维护，`memory_search` 能走向量，但**不自动往 prompt 塞** |
| `true` | `true` | **全开**。索引 + 自动注入 |

**中间那档是刻意做的** —— 可以先只开索引观察几天，确认检索质量之后再开自动注入。
不用为了观察而被迫接受注入。

**关键词权重不单独暴露**，恒等于 `1 - vectorWeight`。

> **这是硬约束，必须写进代码。** 若允许两个权重独立填，
> 用户填 `0.3 / 0.3` 会让总分整体缩到 0.6 倍，**所有结果被 minScore 静默误杀**，
> 表现为"检索突然变差了"，且不报任何错。

## 三、设置页布局

位置：`client.js` L490 后，新增「向量检索」分组。

```
[向量检索]
  启用            □ 语义检索
                    把对话向量化，用于语义召回（关掉 = 纯关键词）
  自动注入        □ 把检索到的历史自动注入当前对话
                    （未启用时置灰）
  同步间隔        [10] 分钟
  最低相关度      [0.62]  低于此分不注入

  ▸ 高级参数
      候选池        [24] 条
      注入条数      [6] 条
      向量权重      [0.70]  关键词权重自动为 0.30
      单条截断      [200] 字  注入时每条最多多少字
```

**依赖关系：**

- `启用` 关闭 → 下面四项全部置灰
- `自动注入` 只在 `启用` 开时可勾
- `最低相关度` 只在 `自动注入` 开时有意义（不注入就不需要阈值）→ 也置灰

**为什么阈值跟自动注入绑定** —— 它只管"注不注入"，`memory_search` 手动调用时
不受它影响（手动调用由模型自己判断要不要用）。

## 四、首次开启的确认弹窗

**触发条件**：勾选「启用」时，如果 `vec_state` 里还没有建过索引（`total == 0`）。

**不弹的情况**：之前建过（`total > 0`），只是关掉又打开 —— 没有首次那笔大开销，
不需要吓人。

**弹窗内容（不含任何硬编码数字）：**

```
┌─────────────────────────────────────┐
│  建立向量索引                        │
│                                     │
│  将对库里的对话建立索引。             │
│                                     │
│  首次全量索引视机器配置与数据量而定，  │
│  可能从数分钟到数小时不等，期间会持续  │
│  占用 CPU，机器可能变慢。             │
│                                     │
│  之后只做增量更新，通常很快。          │
│                                     │
│  随时可以暂停。                      │
│                                     │
│            [取消]  [确认开始]        │
└─────────────────────────────────────┘
```

> **这里是公共插件，不是只服务本机。**
> 条数、耗时、CPU 占用都因机器而异的，**弹窗里一个具体数字都不写**。
> 唯一可以写的是"从数分钟到数小时不等"这种量级描述。

**「取消」= 不写入配置**，勾选框弹回未选中。**功能不打开。**

**为什么不做"开始按钮"** —— 确认弹窗已经承担了"开始"的职责，
再多一个按钮是冗余。

## 五、索引状态与进度条

进入「记忆注入」Tab 时拉一次 `vectorStatus()`。

### 三种展示

**⓪ 覆盖近期记忆（第 1 趟，通常几分钟）**

```
[向量索引]
  正在覆盖近期记忆 · 2,041 / 2,926 条 · 69.7%
  ███████████████████░░░░░░░

  完成后近期对话即可被检索         [暂停]
```

**① 建立索引中（第 2 趟，剩余全量）**

```
[向量索引]
  正在建立索引
  4,231 / 14,632 条 · 28.9%
  ████████░░░░░░░░░░░░░░░░░░░░  约 62 分钟

  单条 329 ms                    [暂停]
```

条数来自实时查询，ETA 来自**本机实测速率**，两者都不写死。

**② 更新索引中（增量）**

```
[向量索引]
  正在更新索引（+12 条）  ██░░░░
```

**③ 已最新**

```
[向量索引]
  ✓ 索引已是最新
  14,632 条 · 最后同步 14:32
```

**④ 已暂停**

```
[向量索引]
  ⏸ 索引已暂停
  4,231 / 14,632 条 · 28.9%
  ████████░░░░░░░░░░░░░░░░░░░░
                          [继续]
```

### 判据：按任务类型，不按条数

**不用"待处理条数超过某个阈值"来判断** —— 那个阈值必然依赖数据规模：
小库（1,000 条）500 是半壁江山，大库（100 万条）500 微不足道。
**公共插件不能这么拍。**

改成由**后端明确告诉前端当前在跑什么任务**：

| `phase` | 含义 | 展示 |
|---|---|---|
| `warming` | **第 1 趟：近期消息优先** | 进度条 + 「正在覆盖近期记忆」 |
| `building` | **第 2 趟：剩余全量** | 进度条 + 百分比 + ETA + 暂停 |
| `updating` | 增量更新中 | 一行小字，无进度条 |
| `idle` | 无待处理 | ✓ + 条数 + 最后同步时间 |
| `paused` | 已暂停 | 进度条（静止）+ 继续按钮 |

**`warming` 单独一档的理由**：第 1 趟只覆盖最近 20%（上限 5000 条），
通常几分钟就完。**它是"让功能尽快可用"的关键一步**，用户在页面上能看见
「近期记忆已就绪」比看见一个匀速爬的百分比更有意义。

**判定逻辑在后端一处实现：**

```js
// 首次 = 水位线从 0 开始推进；增量 = 已有水位线之上追加
phase = paused                          ? "paused"
      : task?.kind === "warmup"         ? "warming"
      : task?.kind === "build"          ? "building"
      : task?.kind === "update"         ? "updating"
      : "idle";
```

**"首次"的判据是 `watermark_before === 0`**（这张表从没建过索引），
不是"待处理条数多"。后者在任何规模下都不可靠。

### 轮询策略

```
pending > 0  →  每 3 秒轮询 vectorStatus()
pending == 0 →  停止轮询，只在点「刷新」时拉
离开 Tab     →  清理定时器
```

**完成后自动停轮询** —— 不空转。

### ETA 必须按本机实测速率算

**不能写死单条耗时**（我们本机 329 ms，别的机器可能 50 ms 也可能 2 s）。

```js
// 后端维护：任务开始时刻 + 已完成条数
avgMs = done > 0 ? (Date.now() - startedAt) / done : null;
etaMinutes = avgMs ? Math.round((total - done) * avgMs / 60000) : null;
```

**自适应任何机器，零硬编码。**

前若干条还没跑完时 `avgMs` 不可信，此时返回 `etaMinutes: null`，
前端显示 **「正在估时…」**，等有样本再出数。

**显示「约 XX 分钟」，不显示「剩 XX:XX」** —— 精确到秒的倒计时必然不准。
超过 60 分钟显示「约 X.X 小时」。

## 六、限速与暂停

### 限速：按比例，不按固定毫秒

**不能写死 `sleep(300ms)`** —— 那是按我们本机 329 ms/条倒推的。
别的机器单条可能只要 50 ms，固定 300 ms 会让它慢 6 倍。

**改成"让出已用时间的固定比例"：**

```js
// 每处理 10 条让出 30% 的已用时间
const spent = Date.now() - batchStart;
if (++count % 10 === 0) await sleep(Math.round(spent * 0.3));
```

**结果：任何机器上，总耗时都稳定变成约 1.3 倍，让出约 23% 的 CPU 时间。**

| 机器 | 无限速 | 限速 |
|---|---|---|
| 本机（329 ms/条） | 81 分钟 | 约 105 分钟 |
| 快机器（50 ms/条） | 12 分钟 | 约 16 分钟 |
| 慢机器（2 s/条） | 8 小时 | 约 10.4 小时 |

**比例恒定，绝对时间自适应。**

**增量时自动无感** —— 一次任务不到 10 条，`count % 10` 触发不了，
一次 sleep 都不做。"后面都很快"依然成立。

### 暂停

**配置里存 `paused: false`（不跨重启持久化，重启后自动续跑）。**

```js
while (cursor < list.length) {
  if (this._paused) { await this._waitResume(); continue; }
  // ... 处理一条
}
```

**暂停语义：**

- 已经处理完的不回退
- **水位线不推进**（下次从上次推进的位置继续）
- 当前正在处理的那一条跑完再停（不中断 embed，避免半条脏数据）

**状态落库** —— `_paused` 存内存即可。重启后自动续跑，
因为水位线是持久的，续跑 = 从水位线往下走。

**不做跨重启持久化暂停** —— 那种"重启后仍然暂停、你以为坏了"的状态更难排查。

## 七、后端接口

### `vectorStatus()`

`index.js` 的 `switch` 里加，和现有 `memoryStatus` 并列：

```js
case "vectorStatus":
  return { ok: true, value: vectorStatus() };
```

**返回：**

```js
{
  enabled: true,
  autoInject: true,
  paused: false,
  phase: "building",       // building | updating | idle | paused
  pending: 10401,          // 待处理条数（实时 COUNT）
  done: 4231,              // 本次任务已处理
  total: 14632,            // 本次任务总量（= done + pending）
  indexed: 4231,           // 库里已有向量总数
  watermark: 38204,
  maxId: 48776,
  lastSyncAt: "2026-11-21T14:32:11+08:00",
  avgMsPerItem: 329,       // 本机实测，动态
  etaMinutes: 62,          // 由 avgMsPerItem 算出，不足样本时为 null
}
```

**`phase`、`avgMsPerItem`、`etaMinutes` 全部由后端算，前端不做任何推断**
—— 避免前后端各算一套对不上，也保证换机器时自动适配。

### `vectorPause()` / `vectorResume()`

```js
case "vectorPause":  return { ok: true, value: vecSync.pause() };
case "vectorResume": return { ok: true, value: vecSync.resume() };
```

### `vectorStatus` 的开销

每次调用要 `COUNT(*)` 一次（待处理条数），**开销随库大小线性增长**。

**所以轮询间隔要跟数据规模挂钩，不能写死 3 秒：**

```js
// 前端只负责按后端给的间隔轮询，不自己判断
pollIntervalMs = status.phase === "building" ? 3000 : 15000;
```

**`building` 阶段进度变化快，3 秒一次；`updating` / `idle` 变化慢，15 秒一次够了。**

库很大时 `COUNT(*)` 会变慢 —— 但只在进入 Tab 且确实有任务时轮询，
**空闲时一次都不查**（`phase === "idle"` 直接停）。

## 九、UI 改动的一个风险

**`client.js` 是 614 行的单文件，三个改动都在里面。**

- 删冻结会话：**独立**，无牵连
- 加设置分组：**独立**，但要注意 `save()` 的字段列表必须同步加
- 加索引状态卡：**依赖 `vectorStatus()` 后端先就绪**

**所以顺序必须是：**

```
① vec-sync.mjs 的 status/pause/resume  →  ② index.js 的 switch case
                                              ↓
                                    ③ client.js 三处改动
```

**先改前端会拿到 `undefined`，页面直接崩。** 这和 11-06 那次
「删硬件历史代码连带切掉 readHardware」是同一类错误 —— 依赖顺序不能反。

## 十、验收

1. 首次勾选「启用」→ 弹确认 → 取消 → **功能未打开、索引未开始**
2. 再次勾选 → 确认 → **进度条出现，每 3 秒更新**
3. 点「暂停」→ **状态变「已暂停」，进度不动** → 点「继续」→ **恢复推进**
4. 索引跑完 → **轮询停止，显示「✓ 索引已是最新」**
5. 关掉「自动注入」（但保留「启用」）→ **索引继续更新，但 prompt 里不再有记忆注入**
6. 刷新页面 → **状态保持正确**
